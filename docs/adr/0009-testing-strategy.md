# Testing strategy: one Vitest runner, four projects, Playwright library inside e2e

All automated tests run under a single Vitest 4 runner configured as four projects, and the gate follows the cache handler's order: `format:check,lint,duplication,typecheck,test,build,pack:check,typecheck:dist,test:e2e`, run from the workspace root and ending in `--gate OK--`. The `test` step is `unit` + `client` + `integration` — Docker is required to pass the gate, as in the sibling cache handler — and `test:e2e` runs last because it needs the built package and example app.

- **`unit`** (`environment: "node"`, Docker-free): Registry types and validation, wire encoding, replay buffer and Cursor logic, Memory Transport, the client core fed synthetic frames through an injected `EventSource`-shaped constructor; fake timers for backoff, type tests next-pipe style.
- **`integration`** (`*.integration.test.ts`, testcontainers): the exported `transportContract` run against Memory and Redis/Valkey containers, **and** two-Instance-in-one-process scenarios — two Transports (and a step up, two `initSSE` instances) on one Prefix exchanging Publishes and Kicks — proving fan-out, replay and Kick across Instances without booting Next.js.
- **`client`** (`environment: "jsdom"`, Docker-free): the React hooks over a `FakeEventSource`, hydrating real `renderToString` output; this is where the handoff-window and reconnect dedup cases are enumerated combinatorially. The `FakeEventSource` ships publicly in `./testing` so consumers test their components the same way, together with the `fakeEventSources()` recorder that hands back every Connection opened through it — the class alone would leave every consumer re-writing the recording subclass, and what a component test asserts on is the Connection, not the constructor (this amends ADR-0008's `./testing` contents, which listed only `transportContract`, and #43 widened the promotion from the class to those two members). The React harness of `react.testkit.ts` stays internal: it would put `react-dom` in the import graph of an entry that has no other reason to hold it, and `mount`/`hydrate` are ten lines the docs can print. The project must **not** set the `react-server` resolve condition.
- **`e2e`** (`e2e/**/*.e2e.test.ts`, one scenario per file, `fileParallelism: false`): the built example app on the cache-handler two-Instance harness (two `next start` on free ports, one container). Protocol scenarios use undici's `EventSource` headless and obtain Cursors from the protocol itself — open a Connection, read the `ready` Control event, close — never by parsing HTML or the RSC payload. Browser scenarios (3–5 files) use the **Playwright library inside the Vitest project, not `@playwright/test`**, Chromium only: real hydration with a Publish stalled inside the handoff window via `page.route`, offline/abort reconnect with no loss or duplicate in the DOM, Instance death with recovery, denial on reconnect. Failover to the surviving Instance goes through a throwaway ~50-line Node `http` proxy in the harness — the only way to test true failover, and the topology real deployments have; restart-on-the-same-port is a secondary scenario, not the substitute. A volume run (a few thousand Messages across two Instances with a mid-run reconnect, asserting exactly-once per Channel) runs on every push; no nightly tier in v0.1.

The e2e suite drives ordinary demo features of the example app (a send action that Publishes, an admin route that Kicks) — no env-gated test-only routes; the tests exercise the same code a reader copies. CI's backend matrix is exactly two cells, `redis:8` and `valkey/valkey:8`, for `integration`; `e2e` runs on `valkey/valkey:8` alone (it exercises the app protocol, not Redis semantics); the local default image is `valkey/valkey:8`. ADR-0006 already bounds commands to Redis 6.2/7.0 features, so older-version cells were dropped as CI time without risk coverage.

Manual multi-Instance runs use `examples/basic/compose.yaml`: two app containers built from the example app's Dockerfile, one Valkey 8 service (Redis as a commented alternative), Caddy as the load balancer (streams SSE without nginx's buffering flags, and doubles as the proxy setup the docs describe). It is purely manual — CI never runs it; the e2e harness already covers two Instances automatically.

## Considered Options

- `@playwright/test` as a second runner: rejected, a second config and runner for 3–5 scenarios with no gain over the library form.
- Vitest browser mode: rejected, the page is served by Vite, not Next.js — it can never render a server component or hydrate Next's HTML, which is the very thing to prove.
- Headless-only e2e (no Playwright at all): rejected, gap-free hydration→SSE handoff is the map's hard requirement and only a real browser proves it end-to-end.
- A Docker-free gate (`test` = unit + client only): rejected, it would let the gate pass without ever exercising Redis; the cache handler already established the Docker-in-gate posture.
- Reading the initial Cursor from the page for headless scenarios: rejected, the Snapshot is opaque (ADR-0007) and parsing the RSC payload couples tests to Next internals.
- A broader image matrix (redis:6.2, valkey 7.2/9): rejected for v0.1; revisit if a feature ever moves past Redis 7.0 commands.
