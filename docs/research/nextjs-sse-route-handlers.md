## Scope and sources

Question: how does a long-lived SSE response behave in a Next.js 16.3 App Router route handler, in `next dev` and `next start`?

Version pin. The latest stable Next.js at time of writing is **v16.3.2** (published 2026-08-21; v16.3.1 on 2026-08-13, v16.3.0 on 2026-08-03, per the GitHub releases API). ## Summary (one screen)

| Topic | Finding |
| --- | --- |
| Streaming | `return new Response(readableStream, { headers })` from `GET` streams chunk-by-chunk through `pipeToNodeResponse`; the stream stays open as long as the handler neither closes nor errors the controller and the client stays connected. Response **headers are not flushed until the first chunk is written**. |
| Disconnect | `request.signal` is wired to the Node `ServerResponse` `'close'` event and aborts with a `ResponseAborted` error when `close` fires before `writableFinished`. The same signal is passed to `readable.pipeTo(...)`, so the `ReadableStream` source's `cancel()` is also invoked. Two independent detection paths. |
| Cache Components | With `cacheComponents: true`, `export const dynamic` (and `revalidate`, `fetchCache`, `dynamicParams`, `runtime`) in `route.ts` is a **build error**, and the `GET` handler **is executed at build time** (twice). The handler must hit a bail-out (read `request.headers`/`cookies()`/`headers()` or `await connection()`) *before* any side effect. Without Cache Components, `GET` handlers are dynamic by default and are not executed at build. |
| Headers | `Content-Type: text/event-stream` (required by the SSE spec), `Cache-Control: no-cache, no-transform` (`no-transform` disables Next's bundled gzip for the stream), `X-Accel-Buffering: no` (nginx). Do **not** set `Connection`/`Keep-Alive` (forbidden in HTTP/2; harmless but useless on HTTP/1.1 where Node sets it). |
| Compression | `next start` and `next dev` wrap every response in `compression@1.7.4` (`compress: true` default). `text/event-stream` is not in mime-db, so `compressible()` falls back to the `^text/` regex and **SSE is gzipped** unless `Cache-Control: no-transform` is set. Next calls `res.flush()` after each chunk so it still works, but a zlib stream is allocated per Connection; a leak on client disconnect was fixed in 16.3.0 (PR #96173). |
| `next dev` | Same request pipeline as `next start` (same `router-server`, same app-route template). Differences: React Strict Mode (default on in App Router) runs effects setup→cleanup→setup, so a `useEffect`-created `EventSource` connects twice; Turbopack server HMR re-evaluates the userland module on every request, so module-scoped state is lost across edits (keep registries on `globalThis` in dev); the dev child process restarts on `next.config.*` change or memory threshold; `SIGINT` in dev calls `server.closeAllConnections()`. |
| HTTP/1.1 vs HTTP/2 | `next start` uses `http.createServer` (HTTP/1.1 only). Browsers cap HTTP/1.1 at 6 connections per origin; HTTP/2 negotiates streams (default 100). HTTP/2 therefore must be terminated by a proxy (nginx/Caddy/Traefik/Vercel) in front of Next. |
| Proxies | nginx buffers by default (`X-Accel-Buffering: no` disables it) and has `proxy_read_timeout 60s` between reads. Caddy and Traefik flush `text/event-stream` immediately and have no read timeout by default. Vercel: streamed responses count toward `maxDuration` (300 s default, 800 s max on Pro/Enterprise) and then the function is terminated. |
| `after()` | Runs callbacks when the response `'close'` event fires (normal end *or* client disconnect). Not a request-time API; does not make the route dynamic. In `next start`, pending `after` work is awaited during shutdown. |
| Lifecycle | `instrumentation.ts` `register()` runs once per server process before the first request, in `next dev` and `next start`, never during `next build`. `next start` installs `SIGINT`/`SIGTERM` handlers that `await server.close()`, which only closes idle connections, so a process with open SSE Connections will not exit until they end (or the orchestrator's kill timeout). `NEXT_MANUAL_SIG_HANDLE=true` disables Next's handlers. |

## 1. Returning a `ReadableStream` and keeping it open

**Docs.** The Route Handler reference shows the Web Streams pattern: `return new Response(stream)` with a `ReadableStream` built from an async iterator (`docs:01-app/03-api-reference/03-file-conventions/route.mdx`, "Streaming"). The streaming guide has a dedicated "Streaming in Route Handlers" section: "Route Handlers can stream raw responses using the Web Streams API. This is useful for Server-Sent Events, large file generation, or any response where you want data to arrive progressively", with an example that enqueues chunks from `start(controller)` and returns `new Response(stream, { headers: { 'Content-Type': 'text/plain; charset=utf-8', 'X-Content-Type-Options': 'nosniff' } })` (`docs:01-app/02-guides/streaming.mdx`, lines 482-570).

**Source.** In the Node runtime the generated route entry (`src:build/templates/app-route.ts`) calls `routeModule.handle(nextReq, context)` and then, for non-ISR routes, `sendResponse(nodeNextReq, nodeNextRes, response, pendingWaitUntil)` (lines 309-375). `sendResponse` copies status and headers onto the Node response and, when `response.body` exists and the method is not `HEAD`, calls `pipeToNodeResponse(response.body, originalResponse, waitUntil)` (`src:server/send-response.ts`). `pipeToNodeResponse` does `await readable.pipeTo(writer, { signal: controller.signal })` where the writer is a `WritableStream` whose `write()` calls `res.write(chunk)`, honours backpressure by awaiting `'drain'` when `res.write` returns `false`, and calls `res.flush()` if the compression middleware added one; `close()` calls `res.end()` (`src:server/pipe-readable.ts`, `createWriterFromResponse`).

Consequences for an SSE handler:

- The response stays open for exactly as long as the `ReadableStream` is neither closed nor errored and the socket is alive. Nothing in Next imposes a duration limit on the Node runtime; `maxDuration` is "for deployment platforms" to enforce (`docs:01-app/03-api-reference/03-file-conventions/02-route-segment-config/maxDuration.mdx`).
- **Headers are flushed lazily.** `createWriterFromResponse` deliberately calls `res.flushHeaders()` inside `write`, not `start`: "this ensures that we don't actually flush the headers until we've started writing chunks" (`src:server/pipe-readable.ts`). Until the handler enqueues its first chunk, the browser has received no status line, `EventSource.onopen` cannot fire (the spec "announces the connection" only on a 200 `text/event-stream` response, WHATWG HTML §9.2.3), and proxy header timeouts keep ticking. An SSE handler should enqueue an initial comment line (`: connected\n\n` or a `retry:` field) immediately.
- Backpressure is handled by Next (awaiting `'drain'`), so a slow consumer slows `pull()`/`enqueue` rather than buffering unboundedly in Node; what accumulates instead is the `ReadableStream`'s internal queue if the source keeps enqueuing without respecting `desiredSize`. (Backpressure policy is on the map's "not yet specified" list; this is the mechanism it will have to work with.)
- Because the Node server's `server.timeout` default is `0` (no inactivity timeout since Node 13; `nodejs/node` `doc/api/http.md`, `server.timeout`), Node itself will not close an idle SSE socket. `server.requestTimeout` (300 s default) only covers "receiving the entire request from the client" and `keepAliveTimeout` (5 s default, `--keepAliveTimeout` on `next start`) only applies "after it has finished writing the last response" (same doc), so neither affects an in-flight SSE response.

## 2. Detecting client disconnect

**Docs.** The Next.js docs do not document `request.signal` for route handlers; the only primary-source example is the e2e test `test/e2e/cancel-request/app/edge-route/route.ts` on canary, which checks `req.signal.aborted` and sets `req.signal.onabort` to abort the stream (found via Context7).

**Source, Node runtime.** The app-route template constructs the handler's `NextRequest` with `NextRequestAdapter.fromNodeNextRequest(nodeNextReq, signalFromNodeResponse(res))` (`src:build/templates/app-route.ts`, lines 283-289). `signalFromNodeResponse` / `createAbortController` are in `src:server/web/spec-extension/adapters/next-request.ts`:

```ts
export function createAbortController(response: Writable): AbortController {
  const controller = new AbortController()
  // If `finish` fires first, then `res.end()` has been called and the close is
  // just us finishing the stream on our side. If `close` fires first, then we
  // know the client disconnected before we finished.
  response.once('close', () => {
    if (response.writableFinished) return
    controller.abort(new ResponseAborted())
  })
  return controller
}
```

The comment on `signalFromNodeResponse` explains why the signal is derived from the *response*, not the request: "This cannot be done with the request (IncomingMessage or Readable) because the `abort` event will not fire if to data has been fully read." Facts that follow:

- `request.signal` fires **once the underlying connection is terminated** (Node `'close'` on `ServerResponse`: "Indicates that the underlying connection was terminated", `doc/api/http.md`). Behind a proxy, that is when the *proxy* closes its upstream connection. nginx does so on client abort by default (`proxy_ignore_client_abort off`: "Determines whether the connection with a proxied server should be closed when a client closes the connection without waiting for a response", nginx `ngx_http_proxy_module`). Caddy/Traefik behaviour on client abort was not verified from primary sources (open question).
- `signal.reason` is a `ResponseAborted` instance (`name === 'ResponseAborted'`), not a DOM `AbortError`. `isAbortError()` in `src:server/pipe-readable.ts` treats both names as abort.
- If the response was already `errored`/`destroyed` when the request object is built, the signal is created pre-aborted and the body is omitted (`fromNodeNextRequest`, "body can not be passed if request was aborted").
- Independently, `pipeToNodeResponse` creates its *own* controller from the same `'close'` event and passes it to `readable.pipeTo(writer, { signal })`; per the Streams standard, aborting a pipe cancels the source, so the handler's `ReadableStream` `cancel(reason)` callback also runs on disconnect. The writer's `abort` calls `res.destroy(err)` unless already finished.
- `request.signal` is *not* one of the properties tracked for dynamic rendering (see §3), so reading it does not by itself make the route dynamic.

In `next dev` the same template and adapter are used; there is no separate code path for dev.

## 3. Cache Components, `'use cache'`, dynamic rendering: what the route must declare

Two models exist in 16.3; which one applies depends on `cacheComponents` in `next.config` (default `false`, `src:server/config-shared.ts` line 2114; the create-next-app template does not set it).

### 3a. Without Cache Components (default)

- "Route Handlers are not cached by default. You can, however, opt into caching for `GET` methods" via `export const dynamic = 'force-static'` (`docs:01-app/01-getting-started/15-route-handlers.mdx`, "Caching"). Version history: in v15.0.0-RC "The default caching for `GET` handlers was changed from static to dynamic" (`docs:.../route.mdx`).
- At build, a `GET` route handler is only executed/prerendered if `isStaticGenEnabled(userland)` is true, i.e. it exports `dynamic = 'force-static'`, `dynamic = 'error'`, `revalidate = false`, `revalidate > 0`, or `generateStaticParams` (`src:server/route-modules/app-route/helpers/is-static-gen-enabled.ts`; gate in `src:export/routes/app-route.ts` lines 106-116, which returns `{ revalidate: 0 }` without calling the handler otherwise).
- `export const dynamic = 'force-dynamic'` is accepted (`src:build/segment-config/app/app-segment-config.ts`, enum `['auto','error','force-static','force-dynamic']`) and at request time sets `workStore.forceDynamic = true` (`src:server/route-modules/app-route/module.ts`, lines 855-866). It is redundant for a plain `GET` handler but makes the intent explicit and protects against a future `revalidate`/`generateStaticParams` export in the same file.
- With `dynamic = 'auto'` (or unset) the `NextRequest` is wrapped in a Proxy that calls `trackDynamic` on access to `headers`, `cookies`, `url`, `body`, `blob`, `json`, `text`, `arrayBuffer`, `formData` and `nextUrl.{search,searchParams,url,href,toJSON,toString,origin}` (`module.ts`, `proxyNextRequest`, lines 1101-1160). Everything else, including `signal` and `method`, passes through untracked.

### 3b. With Cache Components (`cacheComponents: true`)

- Route segment config is removed: "`dynamic`, `dynamicParams`, `revalidate`, and `fetchCache` removed when Cache Components is enabled" (`docs:01-app/03-api-reference/03-file-conventions/02-route-segment-config/index.mdx`, Version History v16.0.0). The enforcement is in the SWC transform: for any `app/**/route.*` (and page/layout/metadata) file, an export named `dynamicParams`, `dynamic`, `fetchCache`, `revalidate`, `experimental_ppr`, or `runtime` produces `Route segment config "<name>" is not compatible with \`nextConfig.cacheComponents\`. Please remove it.` (`crates:next-custom-transforms/src/transforms/react_server_components.rs`, lines 903-968; observed as a Build Error in `test/e2e/app-dir/cache-components-segment-configs/`). The migration guide's answer for `force-dynamic` is "Not needed. All pages are dynamic by default" (`docs:01-app/02-guides/migrating-to-cache-components.mdx`, "dynamic = \"force-dynamic\"").
- But for `GET` route handlers "dynamic by default" means *prerendered if they can be*: "When Cache Components is enabled, `GET` Route Handlers follow the same model as normal UI routes ... They run at request time by default, can be prerendered when they don't access uncached or runtime data" and "Prerendering stops if the `GET` handler accesses network requests, database queries, async file system operations, request object properties (like `req.url`, `request.headers`, `request.cookies`, `request.body`), runtime APIs like `cookies()`, `headers()`, `connection()`, or non-deterministic operations" (`docs:.../15-route-handlers.mdx`, "With Cache Components"). "Reading uncached or runtime data in a `GET` handler bails out of prerendering by **throwing**" (`migrating-to-cache-components.mdx`, "Route Handlers (GET)").
- **The handler body is executed at build time**, twice. `module.ts` lines 427-648: a "prospective" prerender runs the handler to let caches fill, then a "final" prerender runs it again inside `scheduleImmediate`; the returned `Response` body is read with `result.arrayBuffer()`, and if the body has not fully resolved by the next immediate the prerender is aborted with `Route ... couldn't be rendered statically because it used IO that was not cached` (a `DynamicServerError`, lines 599-637 and `createCacheComponentsError`). A streaming SSE body therefore *does* end up dynamic, but only after the handler has run and created whatever it creates (Transport subscriptions, Redis connections, timers) in the build process.
- The clean bail-out points, in order of earliness: synchronous access to a tracked request property (`request.headers`, `request.cookies`, `request.url`, `nextUrl.searchParams`...) throws immediately through `abortAndThrowOnSynchronousRequestDataAccess` ("needs to bail out of prerendering at this point", `src:server/app-render/dynamic-rendering.ts` lines 359-394); `await headers()` / `await cookies()` behave the same for route handlers; `await connection()` returns a promise that never resolves during prerender ("During prerendering it will never resolve and during rendering it resolves immediately", `src:server/request/connection.ts`). Any of these placed before the first side effect keeps the build side-effect-free.
- `'use cache'` "cannot be used directly inside a Route Handler body; extract it to a helper function" (`15-route-handlers.mdx`). Reading request data inside a `'use cache'` scope is an error (`trackDynamic`, case `'cache'`: "Accessing Dynamic data sources inside a cache scope is not supported"). Irrelevant to the SSE handler itself; relevant if Authorize is ever wrapped in a cache.
- `runtime = 'edge'` is unsupported with Cache Components ("Cache Components requires the Node.js runtime", `docs:.../cacheComponents.mdx`); the map already excludes Edge.

### 3c. Why being dynamic is non-negotiable

If the build ever classifies the route as static (it lands in `prerenderManifest.routes`/`dynamicRoutes`), `next start` treats it as ISR: `isIsr` is true, `supportsDynamicResponse` is false, and on a miss the template does `await response.blob()` before caching (`src:build/templates/app-route.ts`, lines 163-166, 200-211, 328-372). An SSE body never ends, so that request would hang forever and never be served. In `next dev`, `supportsDynamicResponse` is always true ("If we're in development, we always support dynamic HTML"), so the problem would only surface in production.

## 4. Required headers and compression

### Headers

- `Content-Type: text/event-stream` is mandatory: the user agent fails the connection "if res's status is not 200, or if res's `Content-Type` is not `text/event-stream`" (WHATWG HTML §9.2.2/9.2.3). Once failed, "it does not attempt to reconnect".
- `Cache-Control`. The Pages Router API-routes doc uses `Cache-Control: no-store` for an event stream (`docs:02-pages/03-building-your-application/01-routing/07-api-routes.mdx`, via Context7). For the App Router nothing is prescribed. Two reasons to send `no-cache, no-transform` (or `no-store, no-transform`): nginx honours `Cache-Control` for `proxy_cache` decisions (nginx `proxy_cache_valid` notes), and `no-transform` is what switches off Next's own gzip (below).
- `X-Accel-Buffering: no`. The streaming guide says: "Nginx and similar reverse proxies buffer responses by default. Disable buffering by setting the `X-Accel-Buffering` header to `no`" and shows it configured via `next.config.js` `headers()` (`docs:01-app/02-guides/streaming.mdx`, "Reverse proxies"). nginx: "Buffering can also be enabled or disabled by passing "yes" or "no" in the "X-Accel-Buffering" response header field. This capability can be disabled using the `proxy_ignore_headers` directive" (`proxy_buffering`, default `on`). Setting it from the handler is equivalent and self-contained.
- `Connection: keep-alive`. Not needed on HTTP/1.1 (Node sets it) and actively wrong for HTTP/2: "Connection, Keep-Alive, Proxy-Connection, Transfer-Encoding, and Upgrade are connection-specific" and an endpoint "MUST treat the presence of a connection-specific header field as a stream error of type PROTOCOL_ERROR"; "intermediaries MUST remove connection-specific header fields before forwarding a message" (RFC 9113 §8.2.2). Proxies strip it, so it is harmless in practice, but there is no reason to emit it.
- `X-Content-Type-Options: nosniff` appears in the official streaming example (`streaming.mdx`). Cheap to add.
- `sendResponse` copies headers verbatim, except it drops `x-middleware-set-cookie` and only appends duplicate names for `set-cookie`, `www-authenticate`, `proxy-authenticate`, `vary` (`src:server/send-response.ts`).

### Compression in `next start` and `next dev`

- "By default, Next.js uses `gzip` to compress rendered content and static files when using `next start` or a custom server" and "If compression is already configured in your application via a custom server, Next.js will not add compression" (`docs:01-app/03-api-reference/05-config/01-next-config-js/compress.mdx`). Default `compress: true` (`src:server/config-shared.ts` line 2080).
- Implementation: `router-server.ts` does `compress = setupCompression()` when `config?.compress !== false` and applies `compress(req, res, () => {})` to every request, dev included (`src:server/lib/router-server.ts`, lines 134-138 and 348-358). The vendored middleware is `compression@1.7.4` (`packages/next/package.json`).
- Whether SSE gets compressed: `compression`'s default filter is `compressible(Content-Type)` (`expressjs/compression@1.7.4` `index.js`, `shouldCompress`). `jshttp/mime-db` has **no entry for `text/event-stream`**, so `compressible` falls back to `COMPRESSIBLE_TYPE_REGEXP = /^text\/|\+(?:json|text|xml)$/i` and returns `true` (`jshttp/compressible` `index.js`). The threshold check (`Number(res.getHeader('Content-Length')) < threshold || length < threshold`) does not block a streamed response because both are `undefined` when `res.flushHeaders()` triggers `onHeaders` (`compression@1.7.4` lines 140-160). Browsers append `Accept-Encoding` at the network layer for every fetch, and `EventSource` uses fetch (Fetch Standard, "HTTP-network-or-cache fetch": "headers such as `Accept-Encoding` ... are to be appended if necessary"). Net result: **under `next start`/`next dev`, an SSE response is gzipped unless opted out.**
- Opt-out: the middleware's `shouldTransform` checks `Cache-Control` for `no-transform` (`/(?:^|,)\s*?no-transform\s*?(?:,|$)/`) and skips compression when present (`compression@1.7.4` lines 146-150). Alternatives: `compress: false` globally (the docs recommend this only when a proxy compresses), or sending a `Content-Encoding` other than `identity` (the middleware then reports "already encoded"; the `Content-Encoding: none` seen in issue #56529 is this hack and is not a valid token).
- If compression is left on, it does work: `createWriterFromResponse` calls `res.flush()` after every `res.write` ("Added by the `compression` middleware, this is a function that will flush the partially-compressed response to the client", `src:server/pipe-readable.ts`). Cost: one zlib stream per Connection for the lifetime of the Connection. Until 16.3.0 the zlib stream of an aborted compressed response was never released (~256 KiB native memory per abort, RSS growth until OOM); fixed by PR [#96173](https://github.com/vercel/next.js/pull/96173) ("fix: release compression stream when client disconnects mid-response", merged 2026-07-25, fixes #94919); the merge commit is an ancestor of `v16.3.0` and not of `v16.2.9`. `releaseCompressionStream` is visible in `router-server.ts` lines 352-358 on the 16.3.2 tag. Whether it was back-ported to 16.2.12 was not verified.

## 5. `next dev` vs `next start`

Shared: both run `start-server.ts` → `router-server.ts` → in-process `render-server` (`renderServer.instance = require('./render-server')`, `router-server.ts` line 244); both use the same app-route template, `sendResponse`, `pipeToNodeResponse`, and the same compression wrapper. There is no HTTP hop between router and renderer in either mode.

Differences that matter for SSE:

- **Process model.** `next dev` `fork()`s a child that runs `start-server` (`src:cli/next-dev.ts`, line 395); the parent relays `SIGINT`/`SIGTERM` and escalates to `SIGKILL`. The child exits with `RESTART_EXIT_CODE` (and is re-forked) when a config file changes ("Found a change in next.config... Restarting the server", `src:server/lib/start-server.ts` lines 580-598) or when the heap approaches the memory threshold (lines 253-269). Each restart drops every open Connection; `EventSource` reconnects on its own (network error → "reestablish the connection", WHATWG §9.2.3).
- **Shutdown.** On `SIGINT`/`SIGTERM`, the cleanup in `start-server.ts` (lines 399-479) calls `server.close()` and, **only when `isDev`**, `server.closeAllConnections()`. In dev Ctrl-C therefore kills open SSE sockets immediately; in production it does not (see §9).
- **Turbopack server HMR.** In Turbopack dev the route module resolves a "live userland snapshot" on every request: "it is called on every request so that server HMR updates are picked up without re-executing the entry chunk" (`src:server/route-modules/app-route/module.ts`, lines 186-194, 355-368, 765-775). An edit to the route file or anything it imports yields a new module instance for subsequent requests; in-flight SSE responses keep running closures from the old instance. Module-scoped state (a Memory Transport, a Connection registry) is therefore duplicated between old and new instances. The official pattern for state that must survive HMR is a `globalThis`-keyed singleton in development (`examples/with-mongodb/lib/mongodb.ts` on the same tag: "In development mode, use a global variable so that the value is preserved across module reloads caused by HMR"). The Next.js *docs* do not describe this; the example is the primary source.
- **React Strict Mode.** "Since Next.js 13.5.1, Strict Mode is `true` by default with `app` router" (`docs:01-app/03-api-reference/05-config/01-next-config-js/reactStrictMode.mdx`). React: "When Strict Mode is on, React will also run one extra setup+cleanup cycle in development for every Effect" (setup → cleanup → setup), development-only (react.dev, `StrictMode`). A hook that opens an `EventSource` in `useEffect` will open, close, and reopen on mount in `next dev`: two connects, one disconnect, one Authorize per Channel twice. Cleanup must call `EventSource.close()`, and the server will see the first Connection's `request.signal` abort.
- **On-demand compilation.** Route modules are compiled on first request in dev (general dev behaviour; the first SSE connect is slower). Not further sourced; noted as observation.
- **Compression** applies in both modes (§4).
- **`supportsDynamicResponse`** is always true in dev, so a route that is accidentally static only breaks in `next start` (§3c).
- **Manual signal handling** "is not available in `next dev`" (`docs:01-app/02-guides/self-hosting.mdx`, `NEXT_MANUAL_SIG_HANDLE`).

## 6. HTTP/1.1 vs HTTP/2 and proxies

- **Next itself is HTTP/1.1 only.** `start-server.ts` creates the listener with `http.createServer(requestListener)` (or `https.createServer` for `--experimental-https`) (lines 273-281); the Node `http` module does not speak HTTP/2 (that is the separate `http2` module, `doc/api/http.md`). HTTP/2 to browsers must come from a proxy or platform in front of `next start`.
- **Per-origin limit on HTTP/1.1.** MDN: "When not used over HTTP/2, SSE suffers from a limitation to the maximum number of open connections, which can be specially painful when opening various tabs as the limit is per browser and set to a very low number (6)... When using HTTP/2, the maximum number of simultaneous HTTP streams is negotiated between the server and the client (defaults to 100)" (MDN `EventSource`). The spec warns the same way: "Clients that support HTTP's per-server connection limitation might run into trouble when opening multiple pages from a site if each page has an EventSource to the same domain" (WHATWG §9.2.7). RFC 9113 §6.5.2: `SETTINGS_MAX_CONCURRENT_STREAMS` "Initially, there is no limit to this value. It is recommended that this value be no smaller than 100". The map's "one Connection per client" decision is what keeps an App inside the HTTP/1.1 budget during local dev and on plain-HTTP deployments.
- **Keep-alives.** The spec's authoring note: "Legacy proxy servers are known to, in certain cases, drop HTTP connections after a short timeout. To protect against such proxy servers, authors can include a comment line (one starting with a ':' character) every 15 seconds or so" (WHATWG §9.2.7). Also: "HTTP chunking can have unexpected negative effects on the reliability of this protocol, in particular if the chunking is done by a different layer unaware of the timing requirements" (same section). Node uses chunked transfer encoding for a body without `Content-Length`, and Next flushes per chunk, so the chunk boundaries are the handler's own.
- **nginx** (`ngx_http_proxy_module`): `proxy_buffering on` by default, overridable per response with `X-Accel-Buffering: no`; `proxy_read_timeout 60s` default, "set only between two successive read operations ... If the proxied server does not transmit anything within this time, the connection is closed", so a heartbeat under 60 s is required unless the operator raises it; `proxy_http_version` defaults to 1.1 since 1.29.7 (1.0 before; 1.1 or 2 recommended for keepalive); `proxy_ignore_client_abort off` default, so client aborts propagate upstream and fire `request.signal`.
- **Caddy** (`reverse_proxy`, global options): `flush_interval` "is ignored and responses are flushed immediately to the client if ... Content-Type: text/event-stream"; transport `read_timeout` and `response_header_timeout` "Default: No timeout"; `stream_timeout` and `stream_close_delay` default to none; server `write`/`read_body`/`read_header` timeouts default to none, `idle` 5 minutes (keep-alive idle only); `protocols` default `h1 h2 h3`, so browsers get HTTP/2 and Caddy speaks 1.1 or 2 to the backend (`versions` default `1.1 2`; with Next it will be 1.1). Shutdown: "By default, the grace period is eternal, meaning connections are never forcefully closed".
- **Traefik** (service `responseForwarding`, entrypoint `transport`): `flushInterval` default 100 ms, "ignored when ReverseProxy recognizes a response as a streaming response; for such responses, writes are flushed to the client immediately"; `respondingTimeouts.readTimeout` 60 s covers "reading the entire request, including the body" (a GET is read instantly), `writeTimeout` 0 s (unlimited), `idleTimeout` 180 s (keep-alive idle); `lifeCycle.graceTimeOut` 10 s default ("give active requests a chance to finish before Traefik stops"), after which open SSE Connections are cut. Forwarding timeouts (`responseHeaderTimeout`, `idleConnTimeout`) were not found on the pages read; defaults not verified.
- **Vercel** (`/docs/functions/limitations`, `/docs/functions/streaming-functions`): "Max duration ... For request handlers, this includes time spent processing the request and sending the response, including streamed responses"; with Fluid compute, Node.js functions default to 300 s, maximum 800 s (Pro/Enterprise; 300 s on Hobby), 1800 s in beta; exceeding it returns 504 `FUNCTION_INVOCATION_TIMEOUT`. Streaming with `Content-Type: text/event-stream` from an App Router `GET` is the documented example. Edge functions "must begin sending a response within 25 seconds" and "can continue streaming data for up to 300 seconds" (Edge is out of scope). Memory Transport cannot work across Vercel instances; Redis/Valkey is the only option there, and Connections will be cut every `maxDuration` and must reconnect gap-free (the map's hard requirement does the rest). Whether Vercel's CDN compresses or alters streamed `text/event-stream` bodies was not found in the pages read.
- **CDNs generally**: "Content Delivery Networks may buffer entire responses before forwarding them to the client. Check your CDN provider's documentation for streaming support" (`streaming.mdx`).

## 7. `after()`

- Reference: "`after` allows you to schedule work to be executed after a response (or prerender) is finished" and it "is not a Request-time API and calling it does not cause a route to become dynamic. If it's used within a static page, the callback will execute at build time" (`docs:01-app/03-api-reference/04-functions/after.mdx`). In Route Handlers, `cookies()` and `headers()` may be called inside the callback. "`after` will be executed even if the response didn't complete successfully." Duration: "`after` will run for the platform's default or configured max duration of your route."
- Source: for app routes, `onClose` is `(cb) => { res.on('close', cb) }` (`src:build/templates/app-route.ts`, lines 260-262) and `AfterContext` runs callbacks from `onClose` (`src:server/after/after-context.ts`, `runCallbacksOnClose`). Node emits `'close'` on a `ServerResponse` both after a normal `end()` and on client disconnect, so for an SSE response `after()` callbacks run **when the Connection closes**, however it closes. That makes `after()` a legitimate hook for "Connection closed" bookkeeping that must outlive the handler's own promise, with one caveat: under Cache Components the build-time prerender also "finishes" and would run the callback if the handler registers it before bailing out (put `after()` after the bail-out point).
- In `next start`, `waitUntil` is an internal `AwaiterOnce` that the server awaits on close (`src:server/next-server.ts`, `createInternalWaitUntil`, lines 2176-2193), which is what the self-hosting guide means by "The Next.js server will finish in-flight requests and execute any pending `after()` callbacks before exiting. Platforms should allow a configurable drain period (10-30 seconds is recommended)" (`docs:01-app/02-guides/self-hosting.mdx`, "after").
- `connection()` inside `after()` throws ("`connection()` inside `after()` while rendering ... is not allowed in this scope", `src:server/request/connection.ts`).

## 8. Known issues and discussions in the Next.js repo

Searched GitHub issues/PRs in `vercel/next.js` for "SSE", "event-stream", "EventSource", "graceful shutdown", "signalFromNodeResponse", "releaseCompressionStream" (2026-08-23). Relevant:

- [#96173](https://github.com/vercel/next.js/pull/96173) (merged 2026-07-25, in 16.3.0+): compression zlib stream leaked on every client disconnect mid-response under `next start`/`next dev`/custom server with default `compress: true`; "Deployments that let a proxy handle compression never see it." Directly relevant to SSE (every Connection is an eventual mid-response disconnect).
- [#97698](https://github.com/vercel/next.js/pull/97698) (open, 2026-08-21): "fix: reuse a single drain listener when piping Node streams through gzip" — a listener accumulation in the gzip piping path; not verified whether it affects Web-stream responses (the `pipeToNodeResponse` path) or only `pipeNodeReadableToNodeResponse`.
- [#56529](https://github.com/vercel/next.js/issues/56529) (open since 2023-10): "uncaughtException: Error: aborted with SSE after client browser close the connection" — reported on `runtime = 'edge'` with a `TransformStream`; a 2024-11 comment reports the same "aborted" error on 15.0.3. Edge is out of scope for next-sse, but it is the only long-lived-SSE issue still open.
- [#45048](https://github.com/vercel/next.js/issues/45048) (closed 2026-02-05): rewrites used to buffer `text/event-stream` bodies (12.3.1); a maintainer-era comment tested 16.1.6 and found SSE "streams correctly through the rewrite ... in dev and production".
- [#51404](https://github.com/vercel/next.js/issues/51404) (open): the App Router docs for manual graceful shutdown still point at `pages/_document.js`. Comments (2025-04 to 2026-02) report that registering `process.on('SIGTERM')` from `instrumentation.ts` runs the handler but the process "still stops immediately" — consistent with Next's own cleanup calling `process.exit(143)` as soon as `server.close()` resolves (§9). [#54522](https://github.com/vercel/next.js/issues/54522) (closed 2025-02) argued the automatic behaviour "is not graceful".
- [#56819](https://github.com/vercel/next.js/pull/56819) "Web Streams cleanup" (2023-10) is where `pipeToNodeResponse` moved to `pipeTo` with an `AbortController` "so that the response can use it to cancel the stream" — the origin of the disconnect behaviour in §2.
- [#94279](https://github.com/vercel/next.js/pull/94279) (open): `unstable_requestSignal` for Server Action cancellation — shows the team is extending request-abort signalling; not relevant to route handlers today.

No open issue was found about SSE bodies being buffered or truncated in Node-runtime route handlers on 16.x.

## 9. `instrumentation.ts` `register()` and Node signal handling (facts only)

Graceful shutdown is fog on the map; these are the facts the future ticket will stand on.

- `register` "is called once when a new Next.js server instance is initiated, and must complete before the server is ready to handle requests. `register` can be an async function" (`docs:01-app/03-api-reference/03-file-conventions/instrumentation.mdx`). Source: `ensureInstrumentationRegistered` memoises a single promise; `registerInstrumentation` returns early when `NEXT_PHASE === 'phase-production-build'`, so `register()` never runs during `next build` (`src:server/lib/router-utils/instrumentation-globals.external.ts`). It is loaded from `<distDir>/server/instrumentation.js`, i.e. a separately bundled module; whether it shares a module instance of `@flefebvre/next-sse` with route bundles was not verified (open question; a `globalThis`-keyed registry sidesteps it).
- `register` runs in both `next dev` (in the forked child) and `next start`, in the same process that serves route handlers (§5). The guide recommends `await import(...)` inside `register` rather than top-level imports, and gating on `process.env.NEXT_RUNTIME === 'nodejs'` because "Next.js calls `register` in all environments" (`docs:01-app/02-guides/instrumentation.mdx`).
- `onRequestError` is invoked for errors the server captures in route handlers (`routeType: 'route'`); an error thrown by an SSE handler after headers are flushed is a case not covered by the docs.
- Next's own signal handling in `next start` (`src:server/lib/start-server.ts`, lines 399-479): unless `process.env.NEXT_MANUAL_SIG_HANDLE` is set, it registers `SIGINT` and `SIGTERM` handlers that (1) `await server.close()` ("first, stop accepting new connections and finish pending requests, because they might affect `nextServer.close()` (e.g. by scheduling an `after`)"), calling `server.closeAllConnections()` only in dev; (2) `await nextServer.close()` (runs `onServerClose` listeners, including the `after()` awaiter) and dev cleanup listeners; (3) `process.exit(130)` for `SIGINT`, `143` for `SIGTERM`. Node's `server.close()` "Stops the server from accepting new connections and closes all connections connected to this server which are not sending a request or waiting for a response" (since v19.0.0 it "closes idle connections before returning"); only `server.closeAllConnections()` closes "active connections ... which are sending a request or waiting for a response" (`doc/api/http.md`). Consequence: with open SSE Connections, step (1) never completes on its own; the process stays up until every Connection ends or the orchestrator sends `SIGKILL`.
- Node semantics the library can rely on: multiple `process.on('SIGTERM')` listeners all run (EventEmitter); once any listener is installed, the default terminate-on-signal behaviour is disabled. A listener that ends every SSE response (so `res.end()` fires `'finish'` then `'close'`) lets Next's `server.close()` resolve and its exit proceed. `NEXT_MANUAL_SIG_HANDLE=true` removes Next's handlers entirely; the docs say to set it "directly in the `package.json` script, and not in the `.env` file" and that "Manual signal handling is not available in `next dev`" (`self-hosting.mdx`). The documented example lives in `pages/_document.js`; there is no App Router-specific doc (issue #51404).
- `next start --keepAliveTimeout <ms>` sets `server.keepAliveTimeout` (`start-server.ts` lines 283-285); the CLI doc recommends making it "larger than the downstream proxy's timeouts" (`docs:01-app/03-api-reference/06-cli/next.mdx`). It concerns idle keep-alive sockets, not open streams.

## Recommendation for next-sse

1. **Route file contract.** `export const { GET } = sse.handlers` must work under both models. The handler returned by `sse.handlers` should, as its *first* statement and before touching any Transport, read request data through a tracked path (`request.headers` / `request.cookies`, which Authorize needs anyway) or `await connection()`. That is the bail-out for Cache Components builds and it is a no-op otherwise. Do **not** have the library tell users to add `export const dynamic = 'force-dynamic'`: it is a build error under Cache Components. Mention it in the docs as optional for non-Cache-Components apps only, or not at all.
2. **First bytes immediately.** Enqueue an initial comment (`: ok\n\n`) plus `retry:` before doing any async work, so headers flush, `onopen` fires, and proxy header timeouts stop. Then run Authorize; on denial, close the stream with a terminal event, or, better, do Authorize *before* returning the Response and answer a non-200 (the spec makes a non-200 a permanent "fail the connection" — good for auth denial, and the client hook can surface it).
3. **Headers emitted by the library.** `Content-Type: text/event-stream; charset=utf-8`, `Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no`, `X-Content-Type-Options: nosniff`. No `Connection`, no `Content-Encoding` hacks. `no-transform` keeps Next's gzip off the stream (one zlib stream per Connection avoided, and no dependency on the 16.3.0 leak fix); document that operators who compress at the proxy should still not compress `text/event-stream`.
4. **Heartbeat.** A comment line every ~15 s by default (spec advice; under nginx's 60 s `proxy_read_timeout` and any CDN idle timeout). Make the interval configurable.
5. **Disconnect handling.** Subscribe to both `request.signal` (`abort`) and the `ReadableStream` `cancel()`; treat either as "Connection closed" and make teardown idempotent. Accept `ResponseAborted` as a normal abort. Use `after()` only if bookkeeping must outlive the handler; it fires on `'close'` in any case.
6. **Dev-mode robustness.** Keep the Instance registry (Memory Transport, Connection table) on a `globalThis` symbol in development so Turbopack HMR does not split Publish from existing Connections; make the client hook Strict-Mode-safe (close in cleanup, tolerate a connect/close/connect burst); expect dev-server restarts and rely on the gap-free reconnect.
7. **Deployment docs.** State plainly that `next start` is HTTP/1.1; HTTP/2 (and thus more than 6 tabs per origin) requires a proxy; give nginx (`proxy_buffering off` or rely on `X-Accel-Buffering`, `proxy_read_timeout` ≥ heartbeat, `proxy_http_version 1.1`), Caddy (works by default), Traefik (works by default; `graceTimeOut` cuts Connections) and Vercel (`maxDuration` cap, Redis Transport required) snippets in the patterns section.
8. **Lifecycle hook for later.** Expose a `sse.closeAll()` (or similar) that ends every Connection with a terminal event; the graceful-shutdown ticket can then decide whether the library installs a `SIGTERM` listener itself (works alongside Next's handlers) or documents `NEXT_MANUAL_SIG_HANDLE`. Register nothing from `instrumentation.ts` by default until that ticket decides.
9. **Testing.** The e2e bed should run `next build && next start` with `cacheComponents: true` *and* `false`, assert the route is not in the prerender manifest, assert no `Content-Encoding` on the SSE response, and assert that killing the client fires the server-side close path (both signal and cancel).

## Open questions

- Does `@flefebvre/next-sse` imported from `instrumentation.ts` share a module instance with the same package imported from `app/**/route.ts` (in `next start`, and in Turbopack dev)? Not verified; `globalThis` registry recommended regardless.
- Does `ai-template` (and therefore `examples/basic`) enable `cacheComponents`? Determines which model the example app exercises by default; the library must support both either way.
- Caddy and Traefik behaviour on client abort: do they close the upstream HTTP/1.1 connection promptly so `request.signal` fires? nginx does (`proxy_ignore_client_abort off`); the others were not verified from primary sources.
- Does Vercel's CDN/compression layer alter or delay `text/event-stream` bodies, and does `Cache-Control: no-transform` matter there? Not found in the pages read.
- PR #97698 (drain-listener accumulation under gzip): does it affect the Web-stream response path, and which release will carry it?
- Has the compression-leak fix (#96173) been back-ported to 16.2.x? Matters only if next-sse supports `next@16.2`.
- Is `request.signal` reliably aborted for Connections that end because the *proxy* idles them out (as opposed to the browser closing)? By construction it should (the upstream socket closes), but it was not tested.
- Backpressure: what should happen when `controller.desiredSize` goes negative for a slow consumer (drop, buffer with cap, close)? On the map's "not yet specified" list; §1 documents the mechanism only.
- First-connect latency in `next dev` due to on-demand compilation of the route: measured value not established.
