# Client hooks: Snapshot handoff, reducer-owned state, the Connection reopens from a hook's Cursor

A server component makes its data live by handing the client one Snapshot: `sse.snapshot(read)` takes the Cursor *before* running the read and returns `{ data, cursor }` as a single opaque value, so the ordering rule of ADR-0001 is enforced by the API and the word "cursor" never appears in App code. `sse.cursor()` (which `snapshot` uses) is cached per request with React `cache`, so however many server components a render has, they share one Cursor and the client performs one reconnect, not several.

The primary client shape is `useChannelState(handle, snapshot, reducers)`: the hook owns the list state, seeds it from `snapshot.data`, advances it with one reducer per event (`upsertBy('id')` ships as the common keyed-merge sugar), and restarts it whenever a new Snapshot prop arrives. Its return also carries `apply(event, payload)` (run a reducer locally, e.g. on a server action's result), `act(event, optimistic, action)` (folds `useOptimistic` + `useTransition` + `apply` into one call; the optimistic payload has the event's wire shape; in-flight payloads come back as `pending`, grouped per event, plus an `inFlight` boolean) and `status`. All of them are optional: echo-only sending, `apply`, and `act` are all supported. `useChannel(handle, handlers, { cursor?, onReset? })` remains the low-level hook; without a Cursor it is live-only and ignores replayed Entries until the first caught-up after it mounts.

**A hook that subscribes with a Cursor makes the shared Connection reopen from that Cursor** (subscriptions are still coalesced on one tick, ADR-0004). This is what makes the handoff and every refetch gap-free without the client ever comparing Cursors: the server replays strictly after the given Cursor and reducers absorb the duplicates other hooks may see. The cost is one reconnect per server render that carries a Snapshot (initial load, a Reset refetch, `revalidatePath`, client-side navigation to a live page).

Reset needs no App code: the provider's default `onReset` is `router.refresh()`, the refreshed server components mint a new Snapshot, and the new prop restarts the hook state; a hook can override `onReset`. A Reset is not a `status` value; the hook statuses are `connecting`, `replaying`, `live` (entered on caught-up), `reconnecting`, `refused`. Hook and helper names are working names; the spec owns the final naming.

## Considered Options

- Explicit handoff (`sse.cursor()` + a cursor prop + `key={cursor}` remounts, handlers into `useState`): rejected as the primary shape, correct but the take-Cursor-before-read order and the Reset wiring are on every page; kept conceptually as the low-level `useChannel` + options path.
- Handle-bound snapshot (`chat({ roomId }).snapshot(read)`, no Handle on the client): rejected, a second snapshot shape whose prop type (`SnapshotOf<typeof sse, 'chat', T>`) was the worst line in the prototype, for no capability the plain Snapshot lacks.
- A client-side ring buffer instead of reconnecting from a hook's Cursor: rejected, the Cursor a server render hands out is the log's tail, usually an Entry on a Channel the client never received, so the client cannot cut by equality (ADR-0001 forbids comparison).
- Refetch-on-send (`revalidatePath` in the action instead of `apply`): rejected as a pattern, every sent Message would cost a full server re-render plus a Connection reconnect, promoting the Reset path to the happy path.
- A `key`/dedup option on the hook: rejected, one `upsertBy` reducer covers the snapshot/replay overlap, Kick replay and action echo alike.
- Optimistic payloads with a placeholder shape of their own: rejected, sharing the event's wire shape is what lets `pending` and the state stay one type.
