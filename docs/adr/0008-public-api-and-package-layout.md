# Public API: six subpath entries, all config on initSSE, redis as a plain dependency

The package ships six subpath entries and **no root export**: `./server` (`initSSE`, `SSEProvider`, `toClientChannels`), `./client` (`createClient`, `SSEClientProvider`, `upsertBy`, the `Snapshot`/`Status` types), `./transport` (the `Transport`/`Publisher`/`Entry` contract types, the error classes, `createPublisher`), `./transport/memory` (`createMemoryTransport`), `./transport/redis` (`createRedisTransport`, `createRedisPublisher`) and `./testing` (`transportContract`). `./server` resolves to the real implementation only under the `react-server` condition; its `default` condition **throws** on import, so a Client Component importing the App's Registry fails at module load in every layer, including Client-Component SSR (per the extraction research, a `browser`-only stub is not enough). `./transport` and below never import Next.js or React: they are what workers and third-party Transport authors hold. The package is ESM-only, Node ≥ 22.12, peers `next >= 16.3.0` and `react >= 19.2.0` plus optional `typescript` and `vitest` (for `./testing`); no zod peer — Standard Schema is a vendored types-only interface — and no next-pipe peer in v0.1.

All configuration lives on `initSSE({ context?, key?, transport?, heartbeat?, maxLifetime? })`; `createSSE(channels)` takes only the channel record, so a hot-reload re-evaluation swaps the Registry and nothing else (ADR-0004's reuse semantics; this amends ADR-0004's placement of `heartbeat`/`maxLifetime` on `createSSE`). `context` is optional — an App with only public Channels writes none and `Ctx` is `undefined`. `transport` omitted means zero-config: `REDIS_URL` set → Redis Transport (lazily imported so the Memory path never loads node-redis), unset → Memory. `redis` is a plain dependency, not a peer, matching the cache handler: installs never break and zero-config needs no install step; the subpath split keeps it unloaded for Memory-only Apps. Factories: `createMemoryTransport({ retention? })` and `createRedisTransport({ url?, client?, prefix?, retention?, operationTimeout? })`, explicit config always winning over the ADR-0006 env table.

Publishing is through bound Handles only — there is **no generic `sse.publish(channel, event, payload)`**; the escape hatch is the Transport's own `publish`. A process outside Next.js cannot import the Registry (it pulls server-only auth code), so it gets `createPublisher<typeof sse>(publisher)` from `./transport`: an `import type` of the Registry plus template-literal channel-string typing (`chat:{roomId}` → `` `chat:${string}` ``) gives typed `publish(channel, event, payload)` with zero runtime channel data and no runtime validation (the wire carries schema Output; consistent with ADR-0006). It covers Messages only; a worker that must Kick writes the documented control-entry envelope raw.

The SSE route path is client-side configuration only: default `/api/sse`, overridden by a `url` prop on `<SSEProvider>`; the server handler never needs its own path. `SSEProvider` is a Server Component and therefore accepts no callbacks; overriding the default Reset behaviour (`router.refresh()`) is done by composition: `SSEClientProvider({ channels, url?, onReset? })` is public in `./client` and `toClientChannels(sse)` in `./server` produces its serialisable Channel data. Reserved names are exactly the real property collisions — Registry keys `handlers`, `channels`, `snapshot`, `kick`; event names `publish`, `snapshot`, `pattern`, `params`, `name` — enforced both at the type level and by a runtime throw. The framework-free client core stays internal in v0.1 (one adapter is a hypothetical seam) and the prototype's `useCoreTrace` debug hook is not shipped.

## Considered Options

- A root `.` export re-exporting the common surface: rejected, the server/client split must be explicit or the throwing `default` condition and the RSC boundary become invisible; follows next-pipe.
- `redis` as an optional peer: rejected, zero-config would break on a missing install and the sibling cache handler already established the plain-dependency posture; node-redis is pure JS.
- Runtime channel definitions in a shared file so workers get real Handles and validation: rejected, it reopens ADR-0002's colocation decision for a marginal gain over the type-only wrapper.
- A generic `sse.publish` beside the Handles: rejected, strictly less typed than a Handle and a second way to do the same thing.
- `onReset` as a prop on `<SSEProvider>`: impossible, functions cannot cross the Server-Component prop boundary; composition via the public client provider replaces it.
- `kick` sugar on `createPublisher`: deferred until a real use case; the wire format is already a stable contract.
- Exposing the client core as a public entry: rejected for v0.1, no second consumer exists until the fetch-based transport does.
