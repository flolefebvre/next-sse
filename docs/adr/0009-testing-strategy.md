# Testing strategy: one Vitest runner, five projects, Playwright library inside e2e

All automated tests run under a single Vitest 4 runner configured as five projects, and the gate follows the cache handler's order: `format:check,lint,duplication,typecheck,test,build,pack:check,typecheck:dist,test:e2e`, run from the workspace root and ending in `--gate OK--`. The `test` step is `unit` + `client` + `integration` — Docker is required to pass the gate, as in the sibling cache handler — and the last gate step, `test:e2e`, is **the post-build test phase**: it runs `e2e` _and_ `example` (#46 added the second project and widened the step; the name is kept so the gate order stated here does not move), because both need the built package and the built example app.

- **`unit`** (`environment: "node"`, Docker-free): Registry types and validation, wire encoding, replay buffer and Cursor logic, Memory Transport, the client core fed synthetic frames through an injected `EventSource`-shaped constructor; fake timers for backoff, type tests next-pipe style.
- **`integration`** (`*.integration.test.ts`, testcontainers): the exported `transportContract` run against Memory and Redis/Valkey containers, **and** two-Instance-in-one-process scenarios — two Transports (and a step up, two `initSSE` instances) on one Prefix exchanging Publishes and Kicks — proving fan-out, replay and Kick across Instances without booting Next.js.
- **`client`** (`environment: "jsdom"`, Docker-free): the React hooks over a `FakeEventSource`, hydrating real `renderToString` output; this is where the handoff-window and reconnect dedup cases are enumerated combinatorially. The `FakeEventSource` ships publicly in `./testing` so consumers test their components the same way, together with the `fakeEventSources()` recorder that hands back every Connection opened through it — the class alone would leave every consumer re-writing the recording subclass, and what a component test asserts on is the Connection, not the constructor (this amends ADR-0008's `./testing` contents, which listed only `transportContract`, and #43 widened the promotion from the class to those two members). The React harness of `react.testkit.ts` stays internal: it would put `react-dom` in the import graph of an entry that has no other reason to hold it, and `mount`/`hydrate` are ten lines the docs can print. The project must **not** set the `react-server` resolve condition.
- **`e2e`** (`e2e/**/*.e2e.test.ts`, one scenario per file, `fileParallelism: false`): the scenarios whose subject is the **built package**, which is why this project runs in the post-build phase, where alone `dist` may be resolved (`example` is the other tenant of that phase; no project of the `test` step may resolve it). The built example app is its main tenant, not its definition — #43 added a scenario that boots no app at all: a plain Node worker, in a package with no Next.js installed, Publishing through the packed artifact. The app scenarios run on the cache-handler two-Instance harness (two `next start` on free ports, one container). Protocol scenarios use undici's `EventSource` headless and obtain Cursors from the protocol itself — open a Connection, read the `ready` Control event, close — never by parsing HTML or the RSC payload. Browser scenarios (3–5 files) use the **Playwright library inside the Vitest project, not `@playwright/test`**, Chromium only: real hydration with a Publish stalled inside the handoff window via `page.route`, offline/abort reconnect with no loss or duplicate in the DOM, Instance death with recovery, denial on reconnect. Failover to the surviving Instance goes through a throwaway ~50-line Node `http` proxy in the harness — the only way to test true failover, and the topology real deployments have; restart-on-the-same-port is a secondary scenario, not the substitute. #45 built those five and settled how: `playwright` is a root devDependency with its install script blocked, so nothing is downloaded at install time and CI asks for the one browser by name (`playwright install --with-deps chromium`); the abort is made at the network, by dropping the sockets the harness proxy holds, because `BrowserContext.setOffline` refuses _new_ requests and leaves an established `text/event-stream` hanging — the heartbeat watchdog's case, and a different one; and restart-on-the-same-port is a second `test()` in the failover file rather than a file of its own, on a process killed where it stands rather than signalled, which is also the shape that is not the deploy. One render = one Cursor is a browser scenario too, and the only place `React.cache` is exercised at all (#35, ruling 9): it counts the `/api/sse` requests a hydrated page makes and reads the Channels and the single `cursor` off the one it finds. One request is the observable _shadow_ of the shared Cursor and not the Cursor itself — the client core coalesces one render's subscriptions onto one Connection whether the Cursors agree or not — and what it rules out is the failure a page pays for: a Connection per Snapshot. A volume run (a few thousand Messages across two Instances with a mid-run reconnect, asserting exactly-once per Channel) runs on every push; no nightly tier in v0.1.
- **`example`** (`examples/*/**/*.test.ts(x)`, `environment: "jsdom"`, Docker-free, added by #46): the example app's own tests, which are consumer code — they resolve `@flefebvre/next-sse` through the exports map against `dist`, exactly as an installed project does, which is why they run in the post-build phase beside `e2e` and never in the `test` step. Two of ADR-0010's ten patterns are tests and live here: _testing your app_, a component test over the public `./testing` entry (`fakeEventSources`, a hand-written ten-line mount, and `snapshotOf(data, cursor)` — #46 promoted a third member, sealing a Snapshot through the very function the server uses, because a Snapshot is opaque by type and every consumer's component test would otherwise open it with a cast), and _custom transport_, the example's own minimal Transport held to the exported `transportContract` with neither optional hook, so the `outage` and `peer` cases are skipped by name. It must **not** set the `react-server` resolve condition, for the same reason `client` must not.

The e2e suite drives ordinary demo features of the example app (a send action that Publishes, an admin route that Kicks) — no env-gated test-only routes; the tests exercise the same code a reader copies. CI's backend matrix is exactly two cells, `redis:8` and `valkey/valkey:8`, for `integration`; `e2e` runs on `valkey/valkey:8` alone (it exercises the app protocol, not Redis semantics); the local default image is `valkey/valkey:8`. ADR-0006 already bounds commands to Redis 6.2/7.0 features, so older-version cells were dropped as CI time without risk coverage.

Manual multi-Instance runs use `examples/basic/compose.yaml`: two app containers built from the example app's Dockerfile, one Valkey 8 service (Redis as a commented alternative), Caddy as the load balancer (streams SSE without nginx's buffering flags, and doubles as the proxy setup the docs describe). It is purely manual — CI never runs it; the e2e harness already covers two Instances automatically.

## Considered Options

- `@playwright/test` as a second runner: rejected, a second config and runner for 3–5 scenarios with no gain over the library form.
- Vitest browser mode: rejected, the page is served by Vite, not Next.js — it can never render a server component or hydrate Next's HTML, which is the very thing to prove.
- Headless-only e2e (no Playwright at all): rejected, gap-free hydration→SSE handoff is the map's hard requirement and only a real browser proves it end-to-end.
- A Docker-free gate (`test` = unit + client only): rejected, it would let the gate pass without ever exercising Redis; the cache handler already established the Docker-in-gate posture.
- Reading the initial Cursor from the page for headless scenarios: rejected, the Snapshot is opaque (ADR-0007) and parsing the RSC payload couples tests to Next internals.
- A broader image matrix (redis:6.2, valkey 7.2/9): rejected for v0.1; revisit if a feature ever moves past Redis 7.0 commands.
