# Redis Transport: one Stream per App, read by one blocking reader per Instance, carrying a versioned Entry envelope

The Redis Transport is one Redis Stream per App, key `{<Prefix>}:log`, and nothing else. `publish` is one `XADD {<Prefix>}:log MAXLEN ~ <retentionCap> * entry <json>`; the Cursor it returns is the stream entry ID (`<ms>-<seq>`, minted on the Redis clock). `read(after)` is `XRANGE {<Prefix>}:log (after + COUNT n`; `tail()` is `XINFO STREAM last-generated-id`, which survives the stream going empty. Every Instance's subscription is a single `XREAD BLOCK 5000 STREAMS {<Prefix>}:log <last-seen>` loop on a `duplicate()`d connection with the per-command timeout disabled, so a blocked read never starves `PING` and is never aborted. The loop checks for a gap where a gap can appear — on the position it _resumes_ from, after a read that failed — and not per batch (#40): it starts from a tail this Transport read itself, so no Cursor of a caller's is in play there, and an `XINFO` between two successful blocks would be a round trip on the hot path that also reports as a gap the ordinary race between a subscription resolving and its first block, which the contract suite says is none. Pub/Sub is not used: it is at-most-once, so it would need the stream anyway for replay, and `XREAD BLOCK` wakes blocked readers on `XADD` with the same one-round-trip latency while surviving the Instance's own Redis reconnect without a gap (the loop reissues `XREAD` from its last ID).

**The Prefix is the only isolation, and it sits inside the hash tag.** Pub/Sub and Streams ignore the database index for the purposes that matter here and node-redis's `keyPrefix` never touches channel names, so the library applies the Prefix itself. `{<Prefix>}:` keeps every key an App will ever own in one cluster slot, which is what lets a later per-Channel design use `MULTI` or Lua across them; the cost, one App never spreading over more than one master, is the v0.1 cost model. A Prefix must be non-empty and contain no `{`, `}`, whitespace or control characters; it is otherwise verbatim. The default is `next-sse`, not derived from the App (nothing at runtime names it reliably): two Apps sharing one Redis under the same Prefix _cross-deliver_ (App A's `chat:42` reaches App B's subscribers of `chat:42`), which the docs state as the reason to set `NEXT_SSE_PREFIX` per App. The database index in `REDIS_URL` is documented as scoping nothing.

**One stream field, `entry`, holding the Entry as JSON; the version lives inside the JSON.** ADR-0005 wants the Transport to round-trip an Entry without knowing its shape, so that a new control kind touches no Transport; flat stream fields would couple the Redis Transport to the union. The JSON is the stable contract an external publisher writes in any language:

```json
{ "v": 1, "type": "message", "channel": "chat:42", "event": "message", "payload": { } }
{ "v": 1, "type": "control", "control": "kick", "key": "user-7" }
{ "v": 1, "type": "control", "control": "kick", "channel": "chat:42" }
```

Both `message` and `control` are documented (an admin service outside Next.js revoking access is a real Kick). Additions within `v: 1` are additive; `v: 2` only for a breaking change. The Memory Transport stores the same object. An event's Standard Schema _Output_ is bounded to `JsonValue` at `channel({ events })` time, so `payload` is what the client receives, typed honestly by construction (`z.date()` is a type error; `z.iso.datetime()` is the fix); no runtime check on the publish path, the bound covers it. On the read path the Instance validates nothing: an unparseable Entry or an unknown `v`, `type` or `control` is skipped and reported once through `onError`; a payload that does not match the schema is delivered as is, external publishers are responsible for it; an Entry whose Channel has no subscriber on this Instance is dropped for free (no Registry lookup, no log: during a rolling deploy, old Instances legitimately see Channels they do not know), logged only under `debug`.

**Retention is a count cap trimmed on every Publish and a time window trimmed by the readers.** `MAXLEN ~ <retentionCap>` rides on every `XADD` (external publishers are told to include it; the Instances trim regardless). There is no time-based stream primitive, so each Instance's reader loop issues `XTRIM {<Prefix>}:log MINID ~ <TIME − retentionWindow>` on a period derived from the window — half of it, capped at one minute (#40), so a short window is trimmed soon rather than in a minute's time and a normal one still costs one command a minute, against the Redis clock; concurrent trims from several Instances are harmless, and the effective window is `retentionWindow` plus up to one trim interval. Enforcing the window at read time only was rejected: it would make `gone` depend on the Instance clock and leave big payloads resident in a quiet App. The Memory Transport applies the same two bounds in process.

**`gone` is honest: the log has dropped something, and the Cursor is below what it still serves.** _Amended by #40, on measurement:_ `max-deleted-entry-id` is maintained by `XDEL` alone — `XADD ... MAXLEN ~`, exact `MAXLEN` and `XTRIM MINID` all leave it at `0-0`, on `redis:8` and `valkey/valkey:8` alike — so the original rule (`after < max-deleted-entry-id`) is vacuous for a log that only ever trims, and is retracted. Trimming removes from the front only, so the implemented rule reads two other `XINFO STREAM` fields, both Redis 7.0 and both on Valkey 8: a Cursor is `gone` when the log has dropped anything at all (`entries-added > length`) **and** sits below the oldest position the log still serves — `recorded-first-entry-id` while the log holds Entries, and `last-generated-id` once retention has emptied it, since `recorded-first-entry-id` resets to `0-0` there while everything up to the position reached is gone. The cost is one Cursor value: the newest dropped Entry, whose successor is the oldest retained one, answers `gone` although nothing after it was lost, which costs that Connection one Reset. The reverse never happens, and that is the direction gap-free delivery depends on. The reader's own gap check on resume uses the same rule, and reports the gap at that same oldest position the log still serves, while resuming just below it (#62): the reported position is handed on to clients, so it has to be one `read` answers rather than the position just below everything the log kept, which is `gone` by construction; resuming one below it is what makes that oldest Entry delivered rather than skipped. A Cursor the Transport cannot parse is `gone` too, so the route answers `200` + `reset` rather than `400`: the Cursor is opaque to the Instance and the client core retries a non-200 with the same URL forever. Known hazard, accepted and documented: deleting the stream key (or `FLUSHALL`) makes the log look untouched, after which an old Cursor resumes as if nothing was missed; operators must not delete the stream while Instances run.

**Client posture and configuration mirror the cache handler.** `connectTimeout` 2 s, `socketTimeout` 15 s, `pingInterval` 10 s, `disableOfflineQueue`, a `reconnectStrategy` that never gives up, lazy connect, `unref()`, a mandatory `error` listener, `withDeadline(operationTimeout)` around `publish`/`read`/`tail`, one `onError(error, operation)` hook; an injected node-redis `client` (standalone, cluster or sentinel, detected structurally) is accepted and `duplicate()`d for the reader. All three kinds are proven on real topologies, not only in unit tests: #57 put the whole contract suite on a three-master cluster through an injected `createCluster` client and on a master watched by a sentinel through an injected `createSentinel` client, in the `integration` project's own matrix, with the outage cases skipped (they need one Transport's own path to the backend cut, which a multi-node client's connections do not offer) and failover left open. **Failover is now observed rather than reasoned about, and the two kinds do not behave alike** (#79): both topologies can be started with one replica per master — opt-in, so the files that never fail over still start three servers and two — and one case per topology promotes a replica under a subscription sitting in its `XREAD BLOCK`, waits until every node of the topology reports the new master, and Publishes. On a **Cluster** the server unblocks the read itself: the demoted node answers `-UNBLOCKED force unblock from blocking operation, instance state changed (master -> replica?)`, so the reader's loop reports one failure through `onError(error, "subscribe")`, waits its 250 ms reissue pause and blocks again — routed by the client to the promoted master. No gap, no Reset; across runs the log is readable again within tens of milliseconds of the promotion and the Publish is delivered about 250 ms after it is accepted — that figure being the reissue pause and not the failover. On **Sentinel** nothing is reported at all: node-redis's Sentinel client carries the reader across by itself, and `CLIENT LIST` shows the blocked read still on the demoted node the moment the promotion is visible and on the new master a second later. A Publish delivered from the demoted node in that window is not a gap and cannot become one — that node is a replica of the new master, `XADD` replicates, stream IDs are monotonic and the Cursor _is_ a stream ID, so what the window costs is replication lag, latency rather than Entries. Measured across runs: readable again and delivered within tens of milliseconds of the promotion, with nothing in the way. Both cases are held to one bound, derived rather than picked: `socketTimeout` (15 s), which is the longest a written `XREAD` can sit on a socket nothing is coming down while node-redis 6.2.x cannot abort it, plus the reissue pause and a round trip — 20 s. Neither kind came near it. The branch no test observes is the _ungraceful_ death of the node a reader sits on — no handover, the socket simply goes away — which is the path the Cluster case does exercise from the other end: the read fails, the loop reports it, resumes from the position it holds and reports a gap only if the log dropped it. The reader's `duplicate({ commandOptions: { timeout: undefined } })` is confirmed to be honoured by all three duplicate implementations, and is kept as the correct defence even though node-redis 6.2.x drops a command's timeout the moment it is written to the socket — so on that version the timeout cannot abort an in-flight `XREAD` whether it is cleared or not, which makes the quiet-log case in those two files a regression guard rather than a discriminating proof. The environment table, parsed in full before `REDIS_URL` is read, unset or empty meaning not given:

| Variable                     | Option                      | Default                 |
| ---------------------------- | --------------------------- | ----------------------- |
| `REDIS_URL`                  | `url`                       | none → Memory Transport |
| `NEXT_SSE_PREFIX`            | `prefix`                    | `next-sse`              |
| `NEXT_SSE_RETENTION_WINDOW`  | `retentionWindow` (seconds) | `300`                   |
| `NEXT_SSE_RETENTION_CAP`     | `retentionCap` (entries)    | `10000`                 |
| `NEXT_SSE_OPERATION_TIMEOUT` | `operationTimeout` (ms)     | `1000`                  |
| `NEXT_SSE_DEBUG`             | `debug`                     | `false`                 |

Retention applies to both Transports, so those names carry no `REDIS`. Only Redis 6.2/7.0 features are used (`MAXLEN ~`, `MINID ~`, `XINFO STREAM` 7.0 fields, `XRANGE (`); nothing Redis 8.x-only, so Valkey 8 is a first-class target. **7.0 is a floor, not a preference** (#40): `gone` is decided on `recorded-first-entry-id` and `entries-added`, so a server that reports neither is refused by name at the first `XINFO STREAM` rather than left answering "nothing was lost" to every Cursor.

## Considered Options

- Pub/Sub for wake-up plus the stream for replay: rejected, two primitives and a replay after every subscriber reconnect for a latency `XREAD BLOCK` already matches; `{<Prefix>}:events` is no longer reserved.
- Prefix derived from the package or App name: rejected, `npm_package_name` exists only under `npm run`, and a `cwd` hash changes with the deploy path.
- No default Prefix when `REDIS_URL` is set: rejected, breaks zero-config for the single-App majority to protect the minority the docs can warn.
- Prefix after the hash tag (`next-sse:{log}`): rejected, scatters an App's future keys across slots.
- Flat stream fields (`type`, `channel`, `event`, `payload`): rejected, readable in `redis-cli` but couples the Transport to the Entry union.
- Version as a separate stream field: rejected, the framing is one field; versioning the library-owned JSON is enough for third-party Transports too.
- `JSON.stringify` semantics for payloads (Dates become strings, `undefined` vanishes): rejected, client types would lie.
- Validating incoming payloads against the schema on every Instance: rejected for v0.1, a schema run per Message per Instance for a publisher that already validated.
- Reporting unknown Channels through `onError`: rejected, spams every old Instance for the length of a rolling deploy.
- Window enforced at read time only: rejected, `gone` would depend on clock skew and memory on the cap alone.
- `MINID` on every `XADD` (needs `TIME` first, two round trips or a script): rejected, the cap is what must hold per Publish; the window can lag a minute.
- `gone` from `first-entry` comparison: _adopted by #40, correcting this line._ It was rejected as lying in both directions; under front-only trimming it lies in one, by one Cursor — the newest dropped Entry reads as `gone` — and never claims a Cursor is good when Entries after it were lost. `max-deleted-entry-id` was measured not to move on trimming at all, which leaves this the only rule a trim-only log can honour short of a second command per Publish, to mint a Cursor carrying the Entry's index.
- A companion epoch key folded into the Cursor to detect a recreated stream: rejected for v0.1, a second key on every read path for an operator error the docs can name.
- `400` for a malformed Cursor (ADR-0004): superseded, the core would retry it forever.
