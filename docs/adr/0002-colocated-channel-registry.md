# Colocated server-only Channel Registry, shared with the client as data

The App declares its Channels in one server-only module: `createSSE({ chat: channel({ pattern, events, authorize }) })`, with Authorize next to the Channel it guards and free to import session or database code. That module is never imported by a Client Component. Instead, the library's `<SSEProvider sse={sse}>` Server Component strips the Registry to an explicit allowlist (`{ key: { pattern, events } }`) and passes it as a prop to its `'use client'` half; Client Components address Channels through type-only Handles (`channels.chat({ roomId })`, typed via `import type` of the server module) and `useChannel` resolves the Channel name from that data at render time.

This follows the measured finding that Next.js 16.3 has no supported way to extract values from a server module into the client bundle: `'use server'` forbids non-function exports, `server-only` poisoning is resolve-time and ignores reachability, a colocated file imported by the client ships Authorize and its database imports verbatim in development, and bundler transforms either cannot separate RSC from SSR (Turbopack) or fail open. Moving the patterns as render-time data, Payload CMS's approach, is bundler-independent and fails closed.

Server Handles are bound to the App, so `chat({ roomId }).message(payload)` publishes without a separate `sse.publish` step; `.publish(event, payload)` remains for dynamic event names.

**`createSSE` refuses any two patterns that can make the same Channel name** — _amended by #68; the original decision compared only literal names, on the stated ground that whether two parameterized patterns collide depends on params the Registry does not have._ That ground was measured and does not hold: a param compiles to `[^:]+`, so it is non-empty and cannot span the separator, and therefore the separators a Channel name holds are the ones its pattern spells out. Two patterns can only meet if they ask for the same number of parts, and then only where every part of one shares a text with the part of the other — literal text and `[^:]+` holes, whose intersection is an ordinary walk over the two (`collidingName` in `internal/pattern.ts`), which also spells out a witness name the error quotes. Ordering settles Authorize and nothing else: the first matching pattern guards a Connection, but a Publish never goes near a Connection, so ordering has no answer for **which schema typed the payload**. Two declarations of one name are one stream of Messages with two typings of it — the Transport carries a name, not a Registry key (ADR-0005) — so a payload valid for one reaches the subscribers of the other, typed by a schema it never satisfied. Refusing the Registry at `createSSE` is what makes a Handle's single-declaration payload typing sound, and it keeps the server and worker publish paths in agreement (ADR-0008): `createPublisher`'s intersection over every matching declaration stays as the type-level backstop for the path where no `createSSE` ever ran.

The check is exact for every pattern whose param names are distinct within it — which is what the type level models, since `ParamsOf` reads a name once — and conservative for a pattern that names one param twice (`{a}:{a}`), whose parts are tied to each other in a way the walk does not carry: such a pair may be refused although no name is actually common to both. The remedy is to rename one of the two params, and erring in that direction is the safe one, since the opposite would let an unsound Registry through. This is a breaking change for an App that today declares colliding patterns, taken before v0.1 deliberately: after release the fix space narrows to documenting the hole.

## Considered Options

- Split registry, `defineChannel` shared and an `authorize` map in a server-only `createSSE`: rejected, two files to keep in step grow unmanageable with many Channels.
- Shared file with Authorize restricted to `(params, ctx)`: rejected, Authorize cannot reach a database directly and its code ships to the browser.
- Client restates each pattern, compiler-checked against the server type: kept as the documented fallback when a provider cannot be mounted.
- Type-only client with `{ key, params }` Handles and no Channel names on the client: rejected, the Connection and devtools lose the readable Channel name for no gain once the provider exists.
- Bundler-level stripping of `authorize` (webpack `issuerLayer`, Turbopack rules, SWC plugin): rejected, unsupported surface, Turbopack cannot reach the SSR layer, and a silent mismatch ships Authorize to the browser.
- Generated per-Channel hooks (`channels.useChat`): rejected, `eslint-plugin-react-hooks` does not recognise `object.useX` as a hook.
- On the overlap of #68 — typing a Handle's payload as the intersection of every declaration its filled name could match, as `createPublisher` does: rejected, a Handle starts from a Registry key and the collision only exists at the name level, so the machinery is heavier and the error lands far from the declaration that caused it. Accepting the overlap and documenting the hazard: rejected, it is a soundness hole in the core publish API and the pitch is soundness. Refusing only the decidable collisions and documenting the rest: rejected as unnecessary, there is no undecidable rest.
